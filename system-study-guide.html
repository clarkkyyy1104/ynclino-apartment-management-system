5. Authentication & Role-Based Access

How Login Works (Step by Step)

  1. User visits any page → [Authorize] attribute redirects unauthenticated users to /Account/Login.
  2. User enters username and password on the login form.
  3. Server looks up username in tblUsers where IsActive = true.
  4. PasswordHelper.Verify() re-hashes the typed password with the stored salt and compares byte-by-byte.
  5. If matched, a Claims Identity is created (UserID, Username, Role) and stored in a browser cookie.
  6. On every request, ASP.NET reads the cookie and populates User.Identity automatically.
  7. Logout clears the cookie via HttpContext.SignOutAsync().

The Three Roles

AdminBuilding manager / owner. The first Admin is the Super Admin (marked with a star badge).Full access to all modules. Can create/edit/delete staff accounts. Super Admin cannot be deleted.

TenantA tenant with a login account linked to their tenant record.Can see their own billing, submit maintenance requests, report/claim lost items. Cannot see other tenants' data.

Special Logic

  • Soft delete: "Delete" actually sets Status = "Inactive". The record, billing history, and maintenance history are all preserved.
  • Optional login: When registering a tenant, you can optionally provide a Username + Password. This creates a tblUser record with Role = "Tenant" and links it to the tenant via UserID.
  • Auto-generated username: The system can suggest a username from the tenant's name.
  • Lease End auto-fill: Selecting a Move-In date automatically sets Lease End to the same date next month. The user can override this.
  • Cannot delete unit with active tenant: The foreign key constraint uses RESTRICT — you cannot delete a unit that has tenants pointing to it.
  • Status filter default: The Tenants list defaults to showing only Active tenants. Select "All" to see inactive ones.
  • Computed property: FullName = FirstName + " " + LastName — not stored in DB, computed on the fly.
Why soft delete?Permanently deleting a tenant would also delete or orphan all their billing records, maintenance requests, and payment history. Soft delete keeps all that history intact while removing the tenant from active management.

13. MVC Pattern — How It Applies Here

MVC stands for Model–View–Controller. It separates the application into three layers, each with a distinct job.

LayerFolder in ProjectJobExample
ModelModels/Defines the data structure and business rules. Maps to database tables. Holds validation annotations.tblUnit.cs defines that UnitNumber must be required and max 20 chars.
ViewViews/The HTML page the user sees. Uses Razor syntax to show data passed from the controller. Never queries the database directly.Views/Units/Index.cshtml loops through a list of units and renders a table row for each.
ControllerControllers/The traffic director. Receives HTTP requests, reads/writes data via EF Core, then passes the result to a View or redirects.UnitsController.Index() queries the database for units, filters them, and passes the list to the View.

Concrete Request Flow Example: Adding a Unit

  1. Browser → User clicks "+ Add Unit". Browser sends GET request to /Units/Create.
  2. Router → ASP.NET matches URL to UnitsController.Create() (GET method).
  3. Controller → Creates an empty UnitViewModel and returns View(vm).
  4. View → Views/Units/Create.cshtml renders the blank form with Bootstrap styling.
  5. Browser → User fills form and clicks "Save Unit". Browser sends POST to /Units/Create.
  6. Controller → Create(UnitViewModel vm) is called. Model state is validated. Duplicate check runs. A tblUnit entity is created and saved via EF Core.
  7. Controller → Sets a TempData["Success"] toast message and redirects to /Units.
  8. Browser → Units list page loads. Toast notification appears at bottom right.

ViewModels vs Models — Why Both?

Database models (tblUnit) mirror the database exactly. ViewModels (UnitViewModel) are tailored for forms — they can have extra validation rules, dropdown lists, computed display properties, and fields not in the database. This keeps the database model clean and the form logic separate.

16. Glossary of Technical Terms

TermPlain English Explanation
ASP.NET Core MVCMicrosoft's framework for building web applications in C#. "Core" means it runs on Linux/Mac/Windows. "MVC" is the design pattern it follows (Model-View-Controller).
Entity Framework Core (EF Core)A tool that lets you work with a database using C# objects (classes) instead of writing SQL commands manually. It automatically translates C# operations into SQL.
SQLiteA lightweight database stored as a single file (app.db). No separate database server is needed — the database runs inside the application itself. Good for development and small-scale apps.
ORMObject-Relational Mapper — a tool (like EF Core) that maps database tables to programming objects so you don't have to write SQL manually.
MigrationA file that describes a database schema change (e.g., add a table, add a column). EF Core applies migrations to keep the database structure in sync with your C# models.
Razor (.cshtml)A template syntax that lets you mix C# code with HTML. The @ symbol starts a C# expression. Files end in .cshtml and are compiled into HTML on the server before being sent to the browser.
Bootstrap 5A popular CSS framework that provides ready-made styles and components (buttons, tables, forms, navigation bars). Used here offline (files stored locally, not loaded from the internet).
ViewModelA C# class designed specifically for a form or view. It can have validation rules, dropdown lists, and display-only properties that aren't stored in the database.
Controller ActionA method inside a Controller class that handles one HTTP request. E.g., UnitsController.Create() handles both GET (show the form) and POST (save the form).
Cookie AuthenticationAfter logging in, the server creates a small encrypted file (cookie) stored in the browser. Every page request sends this cookie back to the server to identify the user without requiring a new login.
ClaimsPieces of identity information stored in the login cookie: UserID, Username, Role. Controllers read these via User.FindFirstValue() or User.IsInRole().
[Authorize] attributeA tag placed on a controller or method that tells ASP.NET "only let logged-in users access this." [Authorize(Roles="Admin")] further restricts to a specific role.
PBKDF2-SHA256A password hashing algorithm. It scrambles a password using a random salt and 100,000 repetitions of SHA-256. The result cannot be reversed to get the original password.
SaltA random 16-byte value added to a password before hashing. Two users with the same password will have different hashes because their salts differ.
Foreign Key (FK)A column that stores the ID of a record in another table, creating a relationship. Example: tblTenants.UnitID links each tenant to their unit in tblUnits.
Cascade DeleteWhen a parent record is deleted, all related child records are automatically deleted too. Example: deleting a tenant also deletes all their billing records.
SET NULL on deleteWhen a parent record is deleted, the foreign key in related records is set to NULL instead of deleting the child. Example: deleting a user account sets tblTenants.UserID = NULL rather than deleting the tenant.
RESTRICT deletePrevents a parent record from being deleted if child records reference it. Example: you cannot delete a unit if active tenants are assigned to it.
Soft DeleteInstead of removing a record from the database, it is marked as inactive (e.g., Status = "Inactive"). The record is hidden from normal views but preserved for history.
Hard DeletePermanently removing a record from the database. Cannot be undone. Used for units and staff accounts.
TempDataA short-lived storage in ASP.NET that survives exactly one redirect. Used here to pass success/error messages to the next page, where they appear as toast notifications.
Antiforgery TokenA hidden security value embedded in every HTML form. The server checks it on POST requests to ensure the form was submitted from a legitimate page, not from a cross-site attack (CSRF protection).
DbContextThe EF Core class (ApplicationDbContext) that represents a session with the database. Used in controllers to query and save data: _context.tblUnits.ToListAsync().
LINQLanguage-Integrated Query — C# syntax for querying collections and databases. Example: .Where(u => u.Status == "Vacant") filters a list of units.
NamespaceA grouping for C# classes to avoid name conflicts. All classes in this system use the namespace YnclinoApartmentManagementSystem.

17. Adviser Q & A

Q: What is the purpose of this system?
The Ynclino Apartment Management System is a web-based system for managing an apartment building. It handles unit management, tenant registration, billing and payments, maintenance requests, and a lost-and-found board. It also provides user account management with role-based access so admins, staff, and tenants each see only what is relevant to them.
Q: What technology/framework did you use and why?
We used ASP.NET Core 8.0 MVC with C# because it is a well-established, Microsoft-backed framework that enforces the MVC design pattern. SQLite was chosen as the database for its simplicity — it requires no separate database server installation, making the system easy to run on any development machine. Entity Framework Core handles all database operations so we don't write raw SQL.
Q: Explain the MVC pattern as used in your system.
Model: C# classes in the Models folder represent database tables and carry validation rules (e.g., tblUnit.cs). View: Razor .cshtml files in the Views folder are the HTML pages users see. Controller: C# classes in Controllers handle HTTP requests — they query the database using EF Core and pass data to views. For example, when a user opens /Units, the UnitsController queries all unit records, then passes the list to Views/Units/Index.cshtml to render.
Q: How many database tables does the system have?
Seven tables: tblUsers, tblUnits, tblTenants, tblBillings, tblMaintenanceRequests, tblLostFoundItems, and tblClaimRequests. The full crud branch uses all seven. The demo crud(copy) branch uses only tblUsers, tblUnits, and tblTenants.
Q: How does authentication work?
The system uses cookie-based authentication built into ASP.NET. When a user logs in, their username and role are stored in an encrypted browser cookie. Each page request checks this cookie. Passwords are never stored in plain text — they are hashed using PBKDF2-SHA256 with a random salt and 100,000 hashing iterations. The [Authorize] attribute on controllers prevents unauthenticated access.
Q: What are the user roles and what can each do?
Admin: full access to everything, including managing staff accounts. SemiAdmin: can manage units, tenants, billing, maintenance, and lost & found, but cannot create or delete staff accounts. Tenant: can view their own billing, submit maintenance requests, and report or claim lost items. They cannot see other tenants' data.
Q: Why is a tenant never deleted — only deactivated?
Permanently deleting a tenant would cascade-delete or orphan all their associated records — billing history, payment records, maintenance requests. We use a soft delete pattern: setting Status = "Inactive" hides the tenant from active views but preserves all historical data. This is important for record-keeping and auditing.
Q: What happens when you try to delete a unit that has tenants?
The system blocks it. The delete confirmation page checks if any active tenants are assigned to that unit. If yes, it redirects back with an error message: "Cannot delete a unit with active tenants." The foreign key relationship uses RESTRICT behavior, enforcing this at the database level as well.
Q: How is the database created and structured?
The database is a SQLite file called app.db, automatically created in the project root when the application runs for the first time. Entity Framework Core Migrations define the schema. On startup (Program.cs), db.Database.Migrate() applies any pending migrations. The ApplicationDbContext.cs file defines all table mappings and relationships (foreign keys, unique constraints, default values).
Q: What are the two branches and why are they different?
The crud branch is the complete production-ready system with all 6 modules, login, and role-based access. The crud(copy) branch is a stripped-down demo version with only Units and Tenants management and no login requirement — it was created when our adviser asked us to not include login yet. The two branches run on different ports (7251 and 7250) so both can run simultaneously.
Q: How does the Billing module know the rent amount for a tenant?
When issuing a bill, selecting a tenant triggers a JavaScript call to a BillingController.GetSuggestedAmount() endpoint. This endpoint looks up the tenant's assigned unit and returns that unit's RentPrice. The amount field is then pre-filled with that value. The admin can still change it manually if needed.
Q: How does the Lease End auto-fill work?
In the Tenant Create/Edit form, a JavaScript event listener watches the Move-In Date field. When a date is selected, the script calculates a date exactly one month later and sets it as the Lease End date. The Lease End field remains editable so the admin can override it if the actual lease term is different.
Q: How are passwords protected?
The PasswordHelper.cs class uses PBKDF2 with SHA-256, 100,000 iterations, and a 16-byte random salt. The salt ensures that two users with the same password will have different stored hashes. The 100,000 iterations make brute-force attacks computationally expensive. The hash is stored as a base64 string (salt + hash combined). Verification uses FixedTimeEquals to prevent timing attacks.
Q: What validation does the system perform?
Server-side validation uses Data Annotations (e.g., [Required], [MaxLength], [Range], [RegularExpression]) on ViewModel classes. EF Core also enforces constraints at the database level (unique indexes, NOT NULL). Client-side validation uses jQuery Unobtrusive Validation (automatically wired by ASP.NET). Custom JavaScript in password.js handles real-time password strength feedback with visual indicators for each rule.
